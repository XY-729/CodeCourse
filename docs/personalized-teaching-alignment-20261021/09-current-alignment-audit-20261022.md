# 原始个性化构想与当前实现复核

检查日期：2026-10-22。代码基线：506da27。此轮不修改应用代码、不写用户数据库、不调用外部模型。真实数据仅通过 SQLite 只读连接复制到内存后检查；创建计划复现在独立临时工作区执行。

## 结论

核心设计方向已接近原始要求，但仍不能判为完整可用。尤其“全量知识树上下文”与默认请求预算冲突，以及桌面计划创建没有调用已实现的根识别函数，是需要先修的实际运行问题。

此前正式回归通过只能证明用例覆盖范围内的行为。本轮增加了真实知识树规模检查和创建入口复现，暴露了小规模清单测试未覆盖的问题。

## 优先修复项

### P0：真实全量树在本地预算检查就被拒绝

来源：backend/app/services/personalization/teaching/generation_context.py:111；backend/app/services/llm_client.py:99、234。

读取本机项目 12 的真实可见知识树，使用与实际生成相同的上下文构建函数。仅树上下文就有 307,953 字符，尚不含问题、项目材料和其余提示词。真实 tokenizer 用量未测量，不能把字符数或字节数称为实际 token 数。

check_request_budget 把完整消息的 UTF-8 字节数当 token 上界，与默认 131,072 的预算比较。仅给该树上下文预留 1 个输出 token，也复现拒绝：

    完整请求超过输入预算（UTF-8 字节上界估算 354196，输出预留 1，总预算 131072）

流式入口还固定预留 65,536 个输出 token。问题不是树被截断，而是包含它的正常请求在网络调用前就会被拦截。

建议：按实际模型容量与 tokenizer/可信估算核对输入和输出预算；将整树编码压缩为稳定短身份、共享字段、无空值的紧凑表示，保留全部可见节点和范围；采集真实输入、缓存命中与输出用量。不能仅把阈值抬高后就宣称解决容量问题。

验收：使用真实规模或至少 1,000 节点的样例，覆盖实际提问、总纲、并发课件入口；验证所有节点仍在请求中，预算按实际容量工作，并保留合理的输出空间。

### P1：桌面创建计划没有触发自动识别根

来源：backend/app/api/projects.py:208；backend/app/services/personalization/teaching/root_recognition.py:9；frontend/src/app/useAppController.ts 的 handleCreateLearningPlan。

根识别函数已存在，但源码中未找到调用者。创建接口仅在用户提供 root_concept_ids 时关联已有根；真实前端创建时只传名称。

在隔离数据库配置假模型并拦截模型调用，实际 POST /api/projects/learning-plan，名称为“cpp基础语法到进阶应用”，结果：

    HTTP 200；root_status=pending；root_concept_ids=[]；树节点数=0；模型调用数=0。

Android 的 createLearningPlan 已调用 identifyPlanRoots，桌面与 Android 不一致。

建议：桌面计划保存后启动根识别任务，成功发布根和计划关联，失败明确保留 pending/错误并提供重试；对多领域计划允许多个根；复用已有规范概念，避免按计划名称重复建根。

验收：从实际前端创建无手选根的新计划，验证识别调用、已有根复用、新根创建、失败重试和跨端一致性。

### P1：旧“已掌握”仍可覆盖新的“暂无记录”，导致术语消失

来源：frontend/src/personalization/termDisplayDecision.ts:47、60；backend/app/api/personalization.py 的 term-display-profiles。

事实状态为 unrecorded 时，前端继续进入旧 knowledgeStatus/manualStatus 兼容分支。对有效 manifest 候选输入 familiarity=unrecorded、manualStatus=null、knowledgeStatus=confirmed，实际决策为 eligible=false、reason=confirmed_knowledge。

后台同时返回事实状态与旧维度判断；历史诊断证据等可以产生这种组合。这个复现是兼容情形测试，不意味着本机所有暂无记录的概念都发生了隐藏。

建议：只要接口提供了新事实状态，含 unrecorded，就以该状态为准；只有完全没有新字段的旧接口数据才走兼容分支。撤销人工声明也不能被旧 mastery 表的值重新覆盖。

验收：新事实 unrecorded + 旧 confirmed、人工已知撤销、历史诊断导入、无新字段的旧接口四种组合；桌面和 Android 同步验证。

### P1：历史数据已整理，实际教学记录仍稀疏

本机项目 12 的当前有效可见节点：946 个。事实状态为 unrecorded 的 937 个、encountered 的 8 个、declared_known 的 1 个；只有 9 个节点有关联事实范围、16 个节点有完整索引中的教学覆盖。

55 个历史教学文档索引均为 schema_version=1，其中 48 个 index_status=pending、2 个 partial、2 个 invalid、3 个 complete；teaching_terms 为 0。历史节点归类不会凭空生成理解记录，这是正确行为，但意味着历史课程尚未充分参与新的防重复与原文定位。

建议：单独开展可预览、可撤销的历史清单补录；优先补用户已标记完成或理解的来源。校验原文摘录和内容版本后关联概念与范围，保留原用户反馈，不从“讲过”推断“已理解”。此补录与日常确认理解分开，不能把补录模型调用塞回确认按钮。

### P2：身份、范围和候选完整性仍需提高

- 活跃树中仍有 13 组相同作用域、领域、显示名称的多身份，包括 std::ref、find_package、git revert 等。需要结合来源核对；确为同义的才能迁移引用后合并，语义不同的应明确区分名称，不能按拼写无条件合并。
- 范围职责键中的 aspect 仍为自由文本，“扩容机制”和“扩容原理”可能被当作不同项。需要为已存在范围提供稳定引用或同义映射，防止换个说法就再次展开。
- 同次清单与术语位置已经校验，但没有可靠方法证明模型列出了正文中的所有陌生概念。应增加已有概念词表的漏标检查，衡量真实生成的遗漏率；不要把“没有数量上限”宣称为“保证一个不漏”。
- 自动补父与新根的语义合理性主要依靠模型。程序已防止循环、越权、过期换父等结构错误，后续宜增加“为什么新建根/为什么没有复用父类”的可审计理由与待归类处理。

## 本轮验证

- 真实数据在内存副本中构建完整上下文；没有调用外部模型，也没有更改用户数据。
- 实际桌面创建计划 API 在隔离数据库复现未触发根识别。
- 使用真实前端决策函数复现“新事实暂无记录 + 旧 confirmed”隐藏清单术语。
- 相关正式回归 test_generation_alignment_b、test_knowledge_tree_forest、test_acceptance_20261022 共 34 项通过。它们的通过不覆盖上述真实规模与遗漏入口问题。

建议顺序：先修预算和桌面自动根入口，再清除旧判断覆盖新事实的分支，随后补历史索引和语义身份/范围整理；最后用同一概念的连续提问、课程完成、确认理解、下一次生成组成真实闭环验收。
